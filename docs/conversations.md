# AI 对话的上下文恢复与知识萃取

一次 AI 对话可能产生三种不同资产。本项目按未来用途分流，而不是把所有聊天都
保存成同一种摘要：

| 以后要做什么 | 使用能力 | 产物 |
|---|---|---|
| 回看一次讨论，理解当时目标、结论和依据 | Conversation Digest v2 | 不可变对话快照 |
| 让另一个 Agent 继续仍在进行的任务 | Task Memory | 持续更新的 `TASK.md` |
| 找出值得长期复用的问题、知识、反思和设计 | Conversation Harvest | 候选分析，必要时路由到现有笔记类型 |

三种能力都不会自动记录聊天。只有明确的保存意图才允许写入 Vault；只要求分析
“哪些值得沉淀”时，Harvest 返回建议但不写文件。

## Conversation Digest v2

### 适合什么时候使用

```text
总结并归档这次讨论，方便以后继续。

保存这次架构评审的目标、决定、依据和未决事项。

把这段排障对话做成上下文摘要，不要写成聊天记录。
```

Digest 是一次连贯讨论的冻结快照。它不持续维护活跃任务状态，也不把所有知识
展开成教程。

### 为什么采用分层结构

“30 秒恢复上下文”是首屏目标，不是整篇 250 词的限制：

1. 最前面的恢复卡片让冷启动读者快速知道目标、状态、当前结论、下一步和关键
   产物；
2. 后续章节保留安全续接所需的边界、决定理由、验证证据和开放问题；
3. 不需要重新阅读原聊天，也不会因过度压缩而丢失关键约束。

标准结构：

```markdown
## 恢复卡片

- **目标**：这次讨论要解决什么
- **状态**：探索中、已决定、暂停或已完成
- **当前结论**：目前最可信的结果
- **下一步**：恢复后首先执行什么，或者明确说明已经关闭
- **关键产物**：文件、笔记、提交、日志、URL，或原对话本身

## 边界与约束

## 决策与依据

## 证据与产物

## 未决事项与下一步
```

恢复卡片最多 12 个非空可见行。详细章节没有固定词数，但不能复述逐轮聊天。

### 怎样判断一篇 Digest 合格

一个没有参加原对话的人：

- 只读恢复卡片，能在约 30 秒内说清目标、状态、结论、下一步和证据位置；
- 继续阅读后，知道哪些边界不能违反、为什么做出当前决定；
- 能区分已验证、推断和待确认内容；
- 不会重复已经证明无效的尝试；
- 不必重读聊天就能安全续接。

结构审计会检查中英文 v2 标题、恢复卡片字段和 12 行上限。自然语言是否真实仍
需要 Agent 根据原对话完成冷读自检；`0 findings` 不等于事实自动正确。

## Conversation Harvest

### 适合什么时候使用

```text
这次对话有哪些值得沉淀的问题、知识、反思和好设计？

复盘刚才的讨论，告诉我哪些内容以后还能复用，哪些不值得保存。

从这段聊天中提炼长期知识；如果有多个候选，先让我选择。
```

Harvest 首版是分析与路由工作流，不是新的 `conversation-review` 类型。它从
五个视角寻找候选：

- 问题：现象、原因或假设、解决办法、验证和状态；
- 知识：原理、适用场景、边界、例子和证据；
- 反思：具体事件、原做法的问题、以后改变什么行为；
- 设计：解决的问题、机制、取舍和复用条件；
- 决定与开放项：已经确认什么，还缺什么证据或选择。

这些视角不要求全部有内容。没有价值的栏目应该省略，而不是由 AI 填充套话。

### 什么内容值得保存

候选项至少满足以下两个条件：

1. 未来可能再次遇到或主动搜索；
2. 重新推导成本较高；
3. 能说明适用条件和不适用边界；
4. 有对话、代码、测试或结果支撑；
5. 会改变未来操作、判断或设计。

每个候选项标记：

- `verified`：有当前对话中的证据；
- `inferred`：合理推导，但尚未验证；
- `open`：仍未解决；
- `skip`：不值得保存，并说明原因。

### Harvest 会不会直接写笔记

| 分析结果 | 行为 |
|---|---|
| 只要求分析 | 返回候选清单，不写 Vault |
| 一个高价值候选，类型明确，且明确要求保存 | 路由到现有类型并写一篇 |
| 多个互相独立的候选 | 先让用户选择，不擅自合并或写多篇 |
| 没有长期价值 | 说明原因并停止，不制造空洞笔记 |

现有类型继续承担长期存储：

- 可复用方法、原理和排障知识 → `learning-note`
- 一个核心洞察、反思或设计原则 → `insight-note`
- 项目特定决定、风险或状态 → `project-note`
- 一次讨论的上下文快照 → `conversation-digest`

## 与 Task Memory 的边界

Task Memory 只在用户明确开启后使用，适合跨 Agent、跨会话继续活跃任务。它的
`status / step / decisions / constraints / artifacts / open` 是当前权威状态。

如果已经存在 `Tasks/<slug>/TASK.md`：

- Digest 可以链接它并保存一次讨论快照；
- Harvest 可以识别其中值得晋升的长期知识；
- 两者都不能复制并争夺任务当前态。

## 常见错误

### 把“沉淀这段对话”总是理解成摘要

这句话可能表示恢复上下文，也可能表示提炼长期知识。意图不明确时，Agent 应只
问一个问题：以后主要是为了继续这项工作，还是复用其中的知识？

### 把问题、知识、反思、设计做成强制栏目

它们是分析视角，不是完成清单。空洞的“以后更细心”和没有取舍的“这是个好
设计”都应该进入 `skip`。

### 把 Digest 当成 Task Memory

Digest 是不可变快照；Task Memory 是持续更新的当前态。正在执行的任务应由
Task Memory 续接。

### 只看审计结果

结构审计能发现旧模板、缺少字段和过长恢复卡片，但不能证明对话总结没有事实
漂移。写入后仍要进行一次冷读：不看原聊天，检查是否真的能安全继续。

## 从旧版 Digest 升级

升级 Skill 不会自动改写真实 Vault 中的自定义模板或历史笔记：

- `outdated-conversation-digest-template` 表示 `Templates/Digest Note.md`
  仍是旧结构，未来仍可能继续生成旧式摘要；
- `missing-conversation-digest-heading` 表示某篇历史 Digest 尚未迁移到 v2；
- 更新模板只影响以后创建的笔记，不代表历史笔记已经获得缺失的上下文；
- 不要为了让审计归零批量填充虚构内容。

没有自定义模板时，可以在明确接受覆盖后使用项目安装器或
`scaffold-templates --force` 刷新模板。已有自定义内容时，应手动合并五个 v2
章节并保留自己的治理规则。历史笔记只在它仍有未来续接价值且原对话或证据可用
时迁移；否则保留 finding 或归档都比编造上下文更可靠。
