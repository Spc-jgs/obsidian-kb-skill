# 方案：让「开放循环」有一个模板派生的定义（#87）

**状态：待裁定的方案，未实现。** 记于 2026-08-25。

## 问题不是词表写少了，是词表手写了

#87 的 MVP 描述里列了一份章节词表（开放问题 / 风险·阻塞 / 下一步 / 待办 / 跟进）。
在参考 Vault 上量它的覆盖：**20 / 138**。上一轮我把这读成「词表漏了大头」，
并建议裁定 web-clip 的 47 条算不算开放循环。那个归结是错的。

模板自己就规定了行动章节，每个类型一个，各带一个 `- [ ]`：

| 模板 | 行动章节 |
|---|---|
| `daily-note` | 待办事项 |
| `meeting-note` | 待办事项 |
| `insight-note` | 影响与后续行动 |
| `person-note` | 跟进事项 |
| `project-note` | 下一步行动 |

按**模板派生**的这 4 个章节名重新量：

```
落在模板章节内:   29
落在模板之外:    109   (79%)
     57  后续行动
     15  可复用的项目落地检查表
     10  Action Items
      8  待解决问题
      6  Next Steps
      4  改进方向（待办）
```

**79% 的 checkbox 写在模板没规定的章节里。** 而「后续行动」——最大的一类，
57 条——**在 web-clip 模板里根本不存在**。web-clip 的章节是「来源与结论 /
问题、前提与适用边界 / 核心知识与原理 / 具体做法与示例 / 验证、风险与限制 /
理解与启发 / 关联笔记」。那 57 条写在一个 Agent 自创的章节里。

这是一个契约缺口，不是一个词表缺口：`deep_capture_contract` 只检查必需章节
**是否缺失**，不检查是否多出章节，所以自创章节从不被报出。

## 三层，各自的判据强度不同

### 第一层：模板派生的章节 —— 机械可靠

词表不手写，从 `core/templates/*.md` 里读出「哪个章节下面有 `- [ ]`」。这与
`template_contract`、`deep_capture_contract`、`conversation_digest_contract`
是同一个模式：契约存在于一处，代码从它派生。

产出 29 条。加上英文变体（下一节）到 45 条。

**为什么这是对的**：模板放一个 `- [ ]` 在某章节下，就是在声明"这里记的是行动
项"。作者接受模板即接受这个声明。任何手写的第二份词表都会与模板漂移，而漂移
不可见——这正是 consistency inventory 反复抓到的形状。

### 第二层：英文变体 —— 需要一次契约扩展

`Action Items` 10 条、`Next Steps` 6 条，语义上就是「待办事项」「下一步行动」。
项目已有处理中英变体的既定做法：`CONVERSATION_DIGEST_HEADING_VARIANTS` 和
`DEEP_CAPTURE_HEADING_VARIANTS` 都是 `(canonical, (variant, ...))` 的元组表。

行动章节应该走同一张表，而不是第三份私有词表。#87 正文里写着「多语言章节名
应走已有中英文模板契约，不建立第三份私有词表」——这一条是对的，照做。

### 第三层：自创章节 —— 不收，但要说出口

剩下 63 条落在模板和变体表都没有的章节里。逐类看：

**「后续行动」57 条**（web-clip 47 / project-note 7 / learning-note 3）。抽样：

```
挑选一个常用中间件（Spring IoC 或 MyBatis）制定两周源码阅读计划   ← 学习意向，无完成态
关注 DeepSeek 后续模型在「持续学习」领域的动作。                  ← 关注意向，永不完成
在需要强审计的业务模块中，考虑引入这种基于事件的快照式日志存储方案。  ← 条件性建议
若使用 Tailscale subnet router，复核 ACL 是否最小权限            ← 条件性建议
下载 Hermes 桌面版体验安装流程                                  ← 真实行动项
```

至少三种性质共用一个语法。**没有可靠的机械判据能把它们分开**，而按 §3、§4 的
教训，靠少量正例定下的判据立不住。

**「可复用的项目落地检查表」15 条**：

```
- [ ] Agent 从哪个目录发现 Skill；
- [ ] 外部 Bug 系统版本、权限和字段契约是什么；
- [ ] 修复分支命名是否与团队规范一致；
```

以分号结尾，是给未来项目复用的**问题清单**，不是任务。它们永远不会被勾掉，
因为它们不是待办。这一类在 `project-note` 里，说明「收窄到 project-note +
insight-note」也不干净——那个建议同样是错的。

**「待解决问题」8 条**：名字像开放问题，但不在任何契约里。归入待裁定。

## 写入侧：不收口的话队列永远追不上

只改读取侧，自创章节会继续产生。两个可选的收口，**建议只做第一个**：

**A. 审计报出模板之外的行动章节**（建议做）
新码，`hygiene`：一个 web-clip 写了「后续行动」，而它的模板契约里没有这个章节。
判据是机械的——章节名不在该类型的模板派生集合与变体表里，且其下有 `- [ ]`。
参考 Vault 上会报 57 条中的 web-clip 那 47 条。**这个数字太大，需要先确认它
是不是在指责一种合理用法**；如果是，那该改的是 web-clip 模板（加一个正式的
行动章节），而不是报告作者。

**B. 写入时拒绝**（不建议）
`create-note --apply` 的拒绝集是「作者重写正文就能清掉」的那一类。自创章节
不属于这一类——它是一个风格判断，不是未完成的脚手架。按 v1.35.0 划定的边界，
不该进拒绝集。

## 历史笔记

**不迁移。** 109 条分布在 49 篇笔记里，跨越两个月。批量重写历史笔记违反
`rules-and-errors.md` 的既有约定（"Never bulk-rewrite historical notes to clear
a finding"），而且这些 checkbox 的性质需要作者逐条判断，不是机械可迁移的。

后果要说清楚：**第一期的队列只覆盖 45 / 138**，其余 93 条要么留在原地不进队列，
要么等作者自己整理。这是这个方案最大的代价，写在这里而不是等它被发现。

## 需要你裁定的三件事

1. **web-clip 该不该有一个正式的行动章节？** 有的话，47 条一次性变合法，队列
   涨到 92；没有的话，它们永远在队列外，而审计会开始报它们。
2. **英文变体表要不要扩到行动章节？** 这是一次契约扩展，会影响 `resume-project`
   等已经读这些章节的地方。
3. **第一期只覆盖 45/138，是否可接受？** 若不可接受，方案要从「模板派生」改成
   「先改模板再迁移」，那是一个大得多的工程。

## 验收（若实施）

- 词表从 `core/templates/*.md` 派生，**一条断言**：手写一份等价词表会失败
  （按对象身份或按派生结果比对），因为等值副本正是这个仓库反复抓到的漂移形状。
- **一条断言要能在实现前红**：模板新增一个带 `- [ ]` 的章节，队列必须自动认它。
- 一条硬负例：代码围栏内、HTML 注释内、模板残留的 `- [ ]` 不进队列（复用
  `link_graph` 的 fence 逻辑，不写第四个扫描器）。
- 一条硬负例：已完成的 `- [x]` 不进队列。
- 计数与本文一致，且附产生它的命令；若不一致，先查语料是否变了再改代码。
- consistency inventory 一行：队列的章节来源 ↔ 模板里带 checkbox 的章节。
